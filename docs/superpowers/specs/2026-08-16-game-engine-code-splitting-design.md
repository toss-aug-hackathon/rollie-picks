# 게임 엔진 초기 번들 분리 설계

## 목표

- Toss WebView에서 설정 화면이 무거운 3D·물리 엔진보다 먼저 렌더링되게 한다.
- 현재 설정, 캐릭터 선택, 배치, 레이스, 결과 흐름과 오류 UI를 유지한다.
- 엔진 준비 전에는 기존 `배경 준비 중...` 상태로 제출을 막아 미완성 게임이 시작되지 않게 한다.
- 프로덕션 빌드 결과에서 초기 진입 청크와 게임 엔진 청크가 실제로 분리됐는지 검증한다.

## 확인된 현재 상태

- 프로덕션 빌드는 성공하지만 단일 `main.js`가 약 4.76MB, gzip 기준 약 1.67MB다.
- `App.tsx`가 `GameCanvas`와 `game/engine.ts`를 정적으로 가져온다.
- `GameCanvas`는 설정 화면에서도 항상 마운트되고, `GameEngine`을 즉시 생성한다.
- `game/engine.ts`가 Three.js, Rapier, GSAP을 정적으로 가져오므로 이 라이브러리들이 초기 청크에 포함된다.
- `SetupScreen`과 `ResultOverlay`도 캐릭터 타입 및 메타데이터를 얻기 위해 `game/engine.ts`를 가져오므로 `GameCanvas`만 동적 로딩해서는 엔진 청크를 분리할 수 없다.
- 기존 `mapReady`, `engineError`, `배경 준비 중...` 상태가 비동기 엔진 준비와 실패를 표현할 수 있다.

## 선택한 접근법

가벼운 캐릭터 정의를 엔진에서 분리하고, `GameCanvas`가 마운트된 뒤 `import('../game/engine')`으로 엔진 구현을 백그라운드 로딩한다.

- React 앱과 설정 화면은 엔진 다운로드·평가를 기다리지 않고 먼저 렌더링된다.
- 엔진은 설정 화면이 표시된 직후 백그라운드에서 준비되므로 사용자가 입력하는 시간을 활용한다.
- 엔진 준비가 끝나기 전에는 기존 제출 버튼의 준비 상태를 유지한다.
- 동적 모듈 로딩 실패도 기존 엔진 초기화 실패 경로로 전달할 수 있다.
- 게임 엔진 청크는 여전히 Vite의 500KB 권장치를 넘을 수 있다. 이는 의도적으로 지연된 기능 청크이며, 성공 기준은 경고 제거가 아니라 초기 청크 축소와 정상 동작이다.

## 대안과 제외 이유

### 경고 한도만 상향

`chunkSizeWarningLimit`을 높이면 출력 메시지는 사라지지만 다운로드, 파싱, 실행 비용은 그대로다. 출시 성능을 개선하지 않으므로 제외한다.

### 제출 후 엔진 로딩

사용자가 설정을 제출할 때 엔진을 처음 불러오면 초기 전송량은 더 작아진다. 그러나 제출 직후 별도의 대기 화면이 필요하고 현재 `mapReady` 기반 흐름을 크게 바꾸므로 제외한다.

### 수동 vendor 청크 분리

Three.js, Rapier, GSAP을 수동 청크로 나누면 캐시 경계는 명확해지지만 정적 import가 유지되는 한 초기 요청 대상은 줄지 않는다. 이번 변경 뒤 측정 결과에서 추가 필요성이 확인될 때만 별도 작업으로 검토한다.

## 구성 변경

### 가벼운 캐릭터 모듈

`src/game/characters.ts`를 추가하고 다음 정의를 이동한다.

- `CharacterKey`
- `ThemeMode`
- `CharacterPreviewMap`
- `CHARACTER_DATA`

`SetupScreen`, `ResultOverlay`, `App`은 이 모듈에서 필요한 값 또는 타입을 가져온다. `game/engine.ts`도 같은 모듈을 사용해 캐릭터 정의의 단일 원천을 유지한다.

### 타입 전용 엔진 참조

`App`과 `GameCanvas`에서 `GameEngine`, `GameEngineOptions`, `LiveRankingItem`처럼 실행 시 필요하지 않은 참조는 `import type`으로 가져온다. TypeScript 컴파일 후 이 import는 제거되어 초기 청크가 엔진 구현을 참조하지 않는다.

### 엔진 동적 로딩

`GameCanvas`의 최초 `useEffect`에서 다음 순서로 처리한다.

1. 캔버스 존재 여부를 확인한다.
2. 테마 준비 상태를 로딩으로 전환한다.
3. `import('../game/engine')`을 호출한다.
4. 컴포넌트가 아직 마운트된 경우에만 `GameEngine`을 생성한다.
5. 기존 테마 설정, `init`, 참가자 동기화, 준비 콜백 순서를 유지한다.
6. import 또는 초기화가 실패하면 기존 `onEngineError`를 호출한다.

정적 `GameCanvas` 컴포넌트 자체는 작은 초기 청크에 남는다. 별도의 `React.lazy` 경계가 필요하지 않아 모듈 다운로드 실패를 기존 오류 UI로 일관되게 처리할 수 있다.

## 수명 주기와 경쟁 조건

- 동적 import가 끝나기 전에 컴포넌트가 언마운트되면 엔진을 생성하지 않는다.
- 엔진 생성 후 초기화 도중 언마운트되면 기존 정리 흐름에서 `destroy()`를 호출한다.
- 비동기 완료 콜백은 취소 상태를 확인한 뒤에만 React 상태와 상위 콜백을 갱신한다.
- 참가자와 테마는 현재 ref를 사용해 로딩 완료 시점의 최신 값을 적용한다.
- 개발 환경의 effect 재실행에서도 폐기된 엔진이 화면이나 콜백을 갱신하지 않게 한다.

## 사용자 경험

- 설정 화면의 레이아웃과 문구는 변경하지 않는다.
- 엔진 준비 전에는 제출 버튼에 기존 `배경 준비 중...` 문구가 표시된다.
- 엔진이 준비되면 기존 문구와 활성 상태로 자동 전환된다.
- 로딩 또는 초기화 실패 시 기존 `게임을 불러오지 못했어요`와 `다시 시도` UI를 표시한다.
- 설정 완료 후 배치, 출발, 레이스, 결과 화면의 순서와 기능은 변경하지 않는다.

## 검증 계획

### 정적 검증

- TypeScript `noEmit` 검사로 타입 전용 import와 이동된 정의의 참조를 검증한다.
- `npm run build`로 프로덕션 번들 생성을 확인한다.
- 빌드 출력에 작은 초기 청크와 별도 게임 엔진 청크가 생성됐는지 확인한다.
- 변경 전 약 4.76MB였던 `main.js`와 변경 후 초기 청크 크기를 비교한다.
- `npm run build:ait`로 실제 업로드용 Apps in Toss 산출물이 생성되는지 확인한다.

### 회귀 검증

- 최초 진입 시 설정 화면이 정상 표시되고 준비 중 버튼이 엔진 준비 후 활성화되는지 확인한다.
- 질문과 참가자 입력, 캐릭터 변경, 테마 변경이 정상 동작하는지 확인한다.
- 배치 → 출발 → 레이스 → 결과 → 재경기 흐름을 확인한다.
- 설정 화면 복귀 후 엔진과 캔버스가 계속 정상 동작하는지 확인한다.
- 엔진 모듈 또는 초기화 실패 시 오류 화면과 다시 시도가 동작하는지 확인한다.
- 브라우저 콘솔에 처리되지 않은 Promise rejection이나 중복 WebGL·물리 인스턴스 오류가 없는지 확인한다.

## 완료 기준

- 일반 Vite 빌드와 Apps in Toss 빌드가 모두 성공한다.
- 초기 진입 코드와 게임 엔진 코드가 서로 다른 청크로 출력된다.
- 초기 청크가 변경 전 `main.js`보다 유의미하게 작아진다.
- 기존 게임 흐름과 오류 처리에 기능 회귀가 없다.
- 남는 대형 청크 경고가 의도적으로 지연된 게임 엔진 청크에만 해당하는지 확인한다.

## 범위 밖

- 게임 물리, 그래픽 품질, 사운드 또는 레이스 규칙 변경
- 이미지 리사이징 및 포맷 변경
- Three.js, Rapier, GSAP 교체
- 설정 제출 이후에만 엔진을 다운로드하는 UX 변경
- 경고를 숨기기 위한 임의의 `chunkSizeWarningLimit` 상향
- 배포 또는 Toss 콘솔 업로드 실행
